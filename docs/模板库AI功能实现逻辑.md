# 模板库 AI 功能实现逻辑

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 更新时间 | 2026-08-20 |
| 覆盖功能 | AI 提取结构模板、AI 提取风格模板、AI 按模板写作 |
| 文档性质 | 技术与产品实现设计 |
| 依据 | 当前模板数据模型、Agent/Workflow BFF、SSE 客户端和 Workflow API 资料 |

## 1. 文档目标

本文档说明模板库相关 AI 功能应如何实现，重点包括：

1. AI 如何从 `.docx`、`.pdf`、`.txt` 文件中提取结构模板。
2. AI 如何从材料中识别风格并生成风格模板。
3. AI 如何同时使用结构模板、风格模板、用户要求和参考文档完成写作。
4. 模型输出如何转换为当前前端的数据结构。
5. Workflow API、Agent API、流式事件和页面状态如何衔接。
6. 如何校验结果，降低结构错乱、风格误判和内容编造。

本文档不把当前模拟函数描述成真实 AI 能力。所有内容均区分“当前实现”和“目标实现”。

## 2. 当前项目中的 AI 能力现状

| 功能 | 当前实现 | 结论 |
| --- | --- | --- |
| 结构模板提取 | `mockExtractFromFile(fileName)` 根据文件名关键词返回预置章节 | 仅为页面演示，没有读取文件正文 |
| 风格模板提取 | `mockExtractStyleFromFile(fileName)` 根据文件名关键词返回推荐规格 | 仅为页面演示，没有分析实际语言风格 |
| 模板数据暂存 | `TemplateWritingInput`、`StyleWritingInput` 使用模块级变量暂存 | 已有数据容器，但没有真实消费方 |
| 模板写作入口 | 原模板写作入口隐藏，风格写作页跳回模板库 | 模板库尚未形成写作闭环 |
| Agent 对话 | `/api/chat` 转发到 Agent API，并透传 SSE | 可用于通用公文对话 |
| Workflow 对话 | `/api/chat/workflow` 使用 `app_id` 发起 Workflow 运行 | 可作为模板提取和模板写作的编排基础 |
| Workflow 输入 | 当前只支持 `query` 和 `document` 两个字符串 | 无法直接传完整模板对象和文件 ID |
| Workflow 输出 | 前端解析 `workflow:start`、`node:start/end`、`RunContent`、`workflow:end` | 已具备过程展示基础 |
| 文稿消息 | Agent 客户端识别 `<!-- 公文开始 -->` 标记 | Workflow 客户端暂未把结果转换为文稿卡片 |

因此，目标实现需要补齐三条独立 AI 链路：

```text
文件 → 结构提取工作流 → 结构模板 JSON → 用户校对 → 保存
文件 → 风格提取工作流 → 风格模板 JSON → 用户校对 → 保存
写作资料 + 结构模板 + 风格模板 → 模板写作工作流 → 文稿
```

## 3. 总体架构

### 3.1 推荐分层

```text
页面层
  ├─ 模板库文件选择、加载状态、编辑确认
  └─ 写作页模板选择、资料填写、流式文稿展示
        ↓
Next.js BFF
  ├─ 用户身份与权限
  ├─ 文件上传/解析请求
  ├─ Workflow 参数适配
  └─ SSE 或非流式结果转发
        ↓
AI Workflow
  ├─ 文件解析节点
  ├─ 规则预处理节点
  ├─ LLM 提取/写作节点
  ├─ JSON Schema 校验节点
  └─ 结果修复与质量检查节点
        ↓
模板服务/文件服务
  ├─ 模板持久化与版本
  ├─ 原文件与解析文本
  └─ 参考文档检索
```

### 3.2 工作流拆分

建议建立三个已发布 Workflow 应用，分别配置独立 `app_id`：

| Workflow | 环境变量建议 | 作用 |
| --- | --- | --- |
| 结构模板提取 | `STRUCTURE_EXTRACT_WORKFLOW_APP_ID` | 从一个或多个文件输出结构模板候选 |
| 风格模板提取 | `STYLE_EXTRACT_WORKFLOW_APP_ID` | 从材料输出风格规格和写作要求 |
| 模板写作 | `TEMPLATE_WRITING_WORKFLOW_APP_ID` | 按结构和风格生成完整文稿 |

不建议把三种任务全部塞进一个提示词，通过自然语言判断任务类型。独立 Workflow 更容易维护输入 Schema、模型参数、评测集和版本。

## 4. 文件进入 AI 前的处理

### 4.1 文件上传

当前模板库文件控件只保留文件名。目标实现应上传真实文件并返回：

```json
{
  "fileId": "file_uuid",
  "fileName": "2026年工作总结.docx",
  "mimeType": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
  "size": 183420,
  "status": "uploaded"
}
```

文件校验：

- 扩展名和 MIME 类型必须同时校验。
- 设置单文件大小上限，例如 20MB；具体值由部署环境确定。
- 查杀病毒和恶意压缩包。
- 加密或损坏文件直接返回可理解错误。
- 文件与当前用户或组织绑定，不能通过猜测 ID 读取他人文件。

### 4.2 正文解析

| 文件类型 | 解析方式 |
| --- | --- |
| DOCX | 读取段落、标题样式、编号、表格、页眉页脚和段落顺序 |
| PDF | 提取文本块、页码、字体大小和坐标；扫描件进入 OCR |
| TXT | 按编码识别后读取，保留换行和空段落边界 |

解析结果不要只返回纯文本，应尽量保留结构证据：

```json
{
  "fileId": "file_uuid",
  "blocks": [
    {
      "blockId": "b1",
      "type": "heading",
      "text": "一、总体情况",
      "levelHint": 1,
      "page": 1,
      "style": "Heading 1"
    },
    {
      "blockId": "b2",
      "type": "paragraph",
      "text": "……",
      "page": 1
    }
  ]
}
```

### 4.3 文本清洗

在调用模型前进行确定性处理：

1. 清除重复页眉、页脚和页码。
2. 合并 PDF 中因换行造成的断句。
3. 保留标题编号、项目符号和表格行列关系作为证据。
4. 识别落款、日期、主送机关等公文特殊区块。
5. 对超长材料按章节切分，但保留全局标题树。
6. 为每个片段保留 `blockId`，便于结果回溯。

模型不应直接处理未经清洗的大段 OCR 文本，否则容易把页眉、页码或目录误识别为正文结构。

## 5. AI 提取结构模板

### 5.1 目标

结构提取不是复制原文，而是从原文中抽象出可复用的写作骨架：

- 有哪些章节。
- 章节之间是什么层级。
- 每一章负责表达什么内容。
- 章节适合自由生成还是固定文本填空。
- 合理篇幅是多少。
- 哪些章节为必写或可选。

事实、单位名称、具体日期、个案数据等不应固化进通用结构模板，除非它们是必须保留的格式文本或占位符。

### 5.2 提取流程

```text
文件解析
  ↓
规则识别候选标题
  ↓
LLM 修正标题边界和层级
  ↓
为每个章节生成写作意图
  ↓
判断提示词模式或填充模式
  ↓
推算篇幅和必写性
  ↓
Schema 校验与后处理
  ↓
结构模板候选
```

### 5.3 标题识别规则

先用确定性规则产生候选，再交给模型判断语义，不能完全依赖模型自由生成。

常见一级标题模式：

- `一、标题`
- `一是……`，仅当它实际承担章节标题功能时识别
- `1. 标题`
- `第一部分 标题`
- DOCX 的 Heading 1 / 标题 1 样式
- PDF 中显著大字号、加粗、独立成行的文本

常见二级标题模式：

- `（一）标题`
- `1.1 标题`
- `1）标题`
- DOCX 的 Heading 2 / 标题 2 样式

排除项：

- 目录中的重复标题。
- 表格列名。
- 页眉、页脚。
- 单独出现的“附件”“联系人”“联系电话”等尾部信息，除非业务明确需要作为模板章节。
- 正文中的“一是、二是”并列句，如果它们不是独立段落标题。

### 5.4 标题规范化

前端会单独显示 `1`、`1.1` 等序号，因此 AI 输出的 `title` 必须去除编号：

```text
原文：一、总体情况
输出：总体情况
```

其他处理：

- 去除多余空格和尾部标点。
- 不得把整段正文作为标题。
- 同级标题重复时，保留语义更完整的一项或增加可区分短语。
- 最多输出两级结构，与当前前端能力保持一致。
- 原文超过两级时，将三级及以下内容合并到最近的二级章节写作要求中。

### 5.5 父子关系

模型输出临时键，不直接生成业务 ID：

```json
{
  "key": "s1-1",
  "level": 2,
  "parentKey": "s1"
}
```

BFF 或前端适配器负责生成 UUID，并把 `parentKey` 转换为 `parentId`。这样可以避免模型生成重复 ID。

规则：

- 一级标题 `parentKey = null`。
- 二级标题必须关联最近且语义合理的一级标题。
- 不允许孤立二级标题。
- 顺序按源文档首次出现位置排列。

### 5.6 章节写作意图

每个章节生成一条简短、可执行的 `generationHint`，结构为：

```text
动作 + 内容范围 + 必要约束
```

示例：

- `概述工作背景、时间范围和总体进展，避免展开具体措施。`
- `分条说明主要任务、责任单位和完成时限。`
- `总结可量化成效，并说明数据口径。`

禁止：

- 直接复述大段原文。
- 写成空泛的“生成本章节内容”。
- 把具体事实误写成永久规则。
- 在提示词中混入与章节无关的整体风格要求。

### 5.7 写作模式判断

#### 选择提示词模式

满足任一条件时优先使用 `prompt`：

- 章节内容需要根据每次任务重新组织。
- 原文主要由事实、数据、分析或措施构成。
- 无法稳定识别固定句式和变量位置。
- 同类文稿中该章节表达方式变化较大。

#### 选择文本+占位符模式

满足以下条件时使用 `fill`：

- 存在应基本保留的固定句式。
- 可明确识别少量变量，例如单位、日期、事项、时限。
- 固定文本占主体，变量填充后即可形成有效段落。

示例：

```text
为进一步做好{{工作事项}}，经研究，决定于{{时间}}在{{地点}}开展{{活动名称}}。
```

占位符规则：

- 使用 `{{中文语义名称}}`。
- 名称简短且可理解，不使用 `变量1`。
- 同一语义变量使用同一名称。
- 不把整段待写内容设置为一个巨大占位符。
- 无法确认的内容不要擅自转换为固定文本。

### 5.8 篇幅范围推算

单文件提取时，可使用源章节有效字符数 `L` 作为参考：

```text
wordCountMin = 向下取整到十位的 0.8 × L
wordCountMax = 向上取整到十位的 1.2 × L
```

补充规则：

- 落款等短格式章节可设置更小范围。
- 原章节明显冗长时，不机械放大，应按文种常规进行修正。
- 多文件提取时优先使用同类章节长度分布的 P25 和 P75，而不是单篇 ±20%。
- 置信度低时允许返回 `null`，由用户决定。
- 中文“字数”以最终产品统一的字符统计口径为准。

### 5.9 必写性和固定标题

`required` 判断：

- 文种成立所必需的章节默认 `true`。
- 原文明确出现“可选、如有、必要时”或仅在特定条件出现的章节可设为 `false`。
- 只有一篇样本文档时，不应仅因某章出现就断定其永远必写；无法判断时默认 `true` 并降低置信度。

`fixedTitle` 判断：

- 法定、制度性或单位明确要求原样保留的标题可为 `true`。
- 一般提取模板默认 `false`，允许用户修改。
- 当前页面尚未实现单章节锁定，字段只能作为预留数据。

### 5.10 AI 输出 Schema

AI 不生成最终模板 ID、章节 UUID 和时间戳，只输出业务内容：

```json
{
  "nameSuggestion": "工作总结结构",
  "documentType": "工作总结",
  "sections": [
    {
      "key": "s1",
      "title": "基本情况",
      "level": 1,
      "parentKey": null,
      "required": true,
      "fixedTitle": false,
      "writingMode": "prompt",
      "generationHint": "概述工作背景、时间范围和总体情况。",
      "fillTemplate": "",
      "wordCountMin": 100,
      "wordCountMax": 300,
      "evidenceBlockIds": ["b3", "b4"],
      "confidence": 0.92
    }
  ],
  "warnings": []
}
```

适配器转换为当前 `WritingTemplate`：

- 生成模板 UUID。
- 为每个 `key` 生成章节 UUID。
- 转换 `parentKey → parentId`。
- 写入 `source = file`、`sourceFileName`。
- 初始化 `referenceFiles = []`。
- 按顺序写入 `order`。
- 写入 `createdAt`、`updatedAt`。

### 5.11 结构提取提示词约束

系统提示词至少应包含：

```text
你是政务写作结构分析器。你的任务是把样本文稿抽象为可复用结构，
不是改写原文，也不是总结事实。

必须遵守：
1. 只输出符合指定 JSON Schema 的 JSON，不输出 Markdown。
2. 标题不得包含“一、”“（一）”“1.”等编号。
3. 最多两级标题，二级标题必须有父级。
4. 个案事实、名称、日期、数字不得固化为通用规则。
5. generationHint 必须说明本章应写什么。
6. 只有固定句式明显时才使用 fill 模式。
7. 不确定时通过 warnings 和 confidence 表达，不得编造。
```

## 6. AI 提取风格模板

### 6.1 目标

风格提取分析“如何表达”，而不是“原文讲了什么”。输出包括：

- 文种。
- 行文方向。
- 受众对象。
- 语气。
- 人称偏好。
- 句式。
- 用词。
- 篇幅节奏。
- 可执行的写作要求。

不得把原文中的业务事实、具体部门、领导姓名、项目名称或结论当成风格要求。

### 6.2 提取流程

```text
解析后正文
  ↓
文种与行文方向分类
  ↓
统计语言特征
  ↓
LLM 归纳风格规格
  ↓
生成可执行写作要求
  ↓
冲突、重复和事实污染检查
  ↓
风格模板候选
```

### 6.3 文种识别

识别依据按优先级排列：

1. 标题中的明确文种词，例如“通知”“请示”“报告”。
2. 结尾固定语，例如“妥否，请批示”“特此通知”。
3. 主送机关和行文关系。
4. 正文结构特征。
5. 文件名只能作为弱证据，不能作为唯一依据。

输出只能是当前前端支持的文种枚举。无法可靠归类时输出“其他”，并在 `warnings` 中说明。

### 6.4 行文方向

| 判断结果 | 典型依据 |
| --- | --- |
| 上行 | 面向上级机关，请示、报告、请求审批 |
| 下行 | 面向下级机关，部署、通知、批复、通报 |
| 平行 | 面向不相隶属单位，协商、征询、函复 |
| 对内 | 面向内部干部、参会人员、内部单位 |
| 对外 | 面向社会公众、企业或外部对象 |

文种与行文方向冲突时，不要强行修正，应保留证据并给出警告，供用户确认。

### 6.5 风格规格提取规则

#### 受众对象

- 归纳为角色群体，不抄具体单位全称。
- 示例：`上级机关`、`下级单位负责人`、`参会干部`。

#### 语气

- 使用 1 至 2 个稳定描述，例如 `严肃正式`、`客观克制`、`谦谨敬重`。
- 不使用无法执行的评价，例如“写得很好”“非常高级”。

#### 人称偏好

- 统计第一、第二、第三人称使用情况。
- 输出主导规则，例如 `第三人称为主`、`第一人称复数为主`。
- 如果原文人称混乱，应说明而不是虚构统一规则。

#### 句式

分析：

- 长短句比例。
- 并列、递进、因果和排比使用情况。
- 段首点题、条目化、问答式等组织方式。
- 输出可执行描述，例如 `短句为主，事项采用并列条目`。

#### 用词

分析：

- 公文规范词、政策术语和专业术语密度。
- 口语化程度。
- 修辞和情绪词使用。
- 输出示例：`使用规范公文用语，减少口语和夸张修辞`。

#### 篇幅节奏

综合段落长度、章节密度和信息展开程度，归纳为：

- 精炼简短。
- 简明扼要。
- 详略得当。
- 条目密集。
- 长篇论述。

### 6.6 写作要求生成规则

写作要求是规格字段的进一步可执行化，建议输出 3 至 8 条：

- 每条只表达一个要求。
- 使用动作或约束表达，例如“通知事项逐条列述，写明责任和时限”。
- 合并同义项，删除空泛评价。
- 不能包含原文具体事实。
- 不能与规格字段冲突。
- 风格不明显的特征不强行输出。

错误示例：

```text
介绍某市2025年完成投资35亿元。
```

正确抽象：

```text
涉及成效时优先使用可核验数据，并说明统计口径。
```

### 6.7 AI 输出 Schema

```json
{
  "nameSuggestion": "领导讲话风格",
  "styleSpec": {
    "documentType": "讲话",
    "direction": "对内",
    "audience": "干部和参会人员",
    "tone": "庄重权威",
    "person": "第一人称复数为主",
    "sentenceStyle": "段首短句点题，主体适度使用排比和递进长句",
    "diction": "政策术语与号召性表达较多，避免网络化口语",
    "lengthRhythm": "长篇论述，重点段落充分展开"
  },
  "writingRequirements": [
    "每个部分先用短句提出核心观点",
    "部署任务时使用并列或递进结构",
    "结尾使用号召性语言收束全文"
  ],
  "evidenceBlockIds": ["b1", "b8", "b12"],
  "confidence": 0.89,
  "warnings": []
}
```

适配器负责生成 ID、来源、来源文件名和时间，转换为当前 `StyleTemplate`。

### 6.8 风格提取提示词约束

```text
你是政务文稿风格分析器。只分析表达方式，不总结业务事实。

必须遵守：
1. 只输出指定 JSON Schema。
2. 文种必须从给定枚举中选择。
3. 不把单位名称、项目、日期、数据和结论写入风格要求。
4. 写作要求必须可执行、单一、去重。
5. 无证据的特征保持为空，不得为了填满字段而编造。
6. 文种、方向或风格存在冲突时写入 warnings。
```

## 7. AI 根据结构模板和风格模板写作

### 7.1 输入对象

完整写作请求至少包含：

```json
{
  "task": {
    "topic": "开展政务数据安全专项检查",
    "documentType": "通知",
    "audience": "各有关单位",
    "additionalNotes": "本月20日前报送整改计划"
  },
  "structureTemplate": {},
  "styleTemplate": {},
  "referenceFiles": [
    { "fileId": "file_1", "scope": "global" }
  ],
  "sectionInputs": {
    "s1": "专项检查背景……"
  },
  "placeholderValues": {
    "时间": "2026年8月25日",
    "地点": "第一会议室"
  }
}
```

模板应传对象或服务端模板 ID+版本，不应把模板名称拼进自然语言后让模型自行猜测。

### 7.2 约束优先级

出现冲突时按以下顺序处理：

1. 安全、权限和系统级规则。
2. 用户本次明确输入及已确认事实。
3. 文本+占位符模式中的固定文本和已确认占位符值。
4. 结构模板中的章节顺序、必写性、生成要求和篇幅。
5. 风格模板中的规格和写作要求。
6. 文种推荐默认值。
7. 模型的一般写作偏好。

用户要求与模板冲突时，系统应尽量以用户本次要求为准，并在生成前提示冲突。不能静默混合成不可预测结果。

### 7.3 写作工作流

推荐使用分阶段生成，而不是一次性把所有内容交给模型：

```text
输入校验
  ↓
事实与占位符准备
  ↓
生成结构执行计划
  ↓
逐章节生成
  ↓
全文组装
  ↓
风格统一
  ↓
结构/事实/篇幅/占位符校验
  ↓
必要时定向修复
  ↓
输出文稿
```

### 7.4 输入校验

生成前检查：

- 结构模板是否存在至少一个章节。
- 所有章节是否有标题和有效写作内容。
- `parentId` 是否有效。
- 篇幅范围是否有效。
- 风格模板字段是否为支持的枚举。
- 参考文件是否存在且有访问权限。
- 填充模式的占位符是否有值或可从资料中提取。

发现缺失时：

- 交互式写作优先询问用户。
- 用户选择“仍然生成”时，用 `【待补：字段名】` 显式标记。
- 不得自行编造日期、金额、单位、责任人和政策依据。

### 7.5 事实准备与参考文档

参考文档分两种作用域：

- 全局参考：所有章节可使用。
- 章节参考：只提供给指定一级标题及其子标题。

处理步骤：

1. 解析文档并切分为带来源 ID 的片段。
2. 根据当前章节标题和 `generationHint` 检索相关片段。
3. 将相关片段与用户输入共同传给章节生成节点。
4. 保留来源信息用于事实核查。
5. 未在资料中出现的关键事实不得补写。

参考文档主要提供事实和表达素材，风格模板负责表达约束，两者职责不能混淆。

### 7.6 结构执行计划

工作流先把模板转换为明确的章节执行计划：

```json
[
  {
    "sectionId": "s1",
    "title": "发文缘由",
    "level": 1,
    "mode": "prompt",
    "instruction": "说明发文背景、依据和目的",
    "min": 100,
    "max": 300,
    "referenceChunkIds": ["chunk_2", "chunk_5"]
  }
]
```

可选章节处理：

- `required = true`：必须生成。
- `required = false`：只有用户输入或参考材料存在相关内容时生成。
- 当前页面没有开放必写性编辑，但写作引擎应支持该字段。

### 7.7 提示词模式章节生成

每个章节单独调用生成节点，输入包含：

- 文稿全局任务。
- 当前章节标题和层级。
- 当前章节 `generationHint`。
- 篇幅范围。
- 父章节和相邻章节的简要上下文。
- 与本章相关的参考片段。
- 风格模板规格和写作要求。

章节提示词示意：

```text
生成章节：发文缘由
本章目标：说明发文背景、政策依据和工作目的。
篇幅：100—300字。
必须依据：ref-2、ref-5。
不得写入：具体检查事项和落款。
风格：通知，下行，严肃正式，短句为主。
只返回章节正文，不返回标题和解释。
```

逐章生成可以避免模型遗漏章节，也便于单独重试和控制篇幅。

### 7.8 文本+占位符模式生成

填充模式以“保持固定文本”为最高原则：

1. 使用解析器提取所有 `{{name}}`。
2. 优先从 `placeholderValues` 读取明确值。
3. 其次从用户输入和参考文档中抽取候选值。
4. 相同占位符在全文使用同一值。
5. 未找到值时询问用户或输出 `【待补：name】`。
6. 替换占位符时不得改写占位符外的固定文本。

实现上不应让 LLM 直接重写整段固定文本。建议由模型只返回键值：

```json
{
  "时间": "2026年8月25日",
  "地点": "第一会议室"
}
```

再由程序完成字符串替换，保证固定文本不被修改。

### 7.9 风格应用

风格约束分为三层：

1. **硬格式约束**：文种、行文方向、人称等。
2. **全局语言约束**：语气、句式、用词、篇幅节奏。
3. **可执行条目**：`writingRequirements`。

风格应从章节生成阶段就进入提示词，而不是全文完成后只做一次“润色”。全文组装后可以再做统一校正，但必须遵守：

- 不改变事实、数字、单位、时间和政策名称。
- 不改变固定文本和已经填入的占位符值。
- 不新增原资料没有的结论。
- 不删除结构模板要求的必要内容。

### 7.10 标题和全文组装

模板标题字段不含编号，最终文稿由组装器根据公文层级渲染：

- 一级标题：`一、标题`。
- 二级标题：`（一）标题`。

若具体文种或排版模板有不同编号规则，由排版层统一处理，不能把编号写死在结构模板标题中。

组装时还需处理：

- 标题前后空行。
- 可选章节跳过后的连续编号。
- 子标题必须跟随父标题。
- 相邻章节重复内容检测。
- 主送机关、落款、日期等公文特殊区块。

### 7.11 结果校验

#### 结构校验

- 所有必写章节是否存在。
- 标题顺序和层级是否与模板一致。
- 是否出现模板外的无关章节。
- 是否存在孤立二级标题。

#### 篇幅校验

- 每章是否落在目标范围。
- 首次偏差在 10% 以内可接受时，由产品设定是否自动修复。
- 偏差过大时只重写对应章节，不重写全文。

#### 占位符校验

- 是否仍有 `{{...}}` 未处理。
- 同名占位符值是否一致。
- 固定文本是否被修改。

#### 事实校验

- 关键数字、日期、单位和政策名称是否能在输入或参考资料中找到。
- 引用资料之间有冲突时是否标记。
- 缺失事实是否使用待补标记，而不是模型补全。

#### 风格校验

- 文种和方向是否一致。
- 人称、语气、句式和用词是否满足模板。
- 写作要求是否逐条覆盖。
- 风格修复不得改变事实。

### 7.12 最终输出

建议 Workflow 非流式最终结果：

```json
{
  "document": "完整文稿正文",
  "sections": [
    {
      "sectionId": "s1",
      "title": "发文缘由",
      "content": "……",
      "wordCount": 186,
      "sourceChunkIds": ["chunk_2"]
    }
  ],
  "validation": {
    "structurePassed": true,
    "placeholdersPassed": true,
    "factWarnings": [],
    "styleWarnings": []
  },
  "templateRefs": {
    "structureTemplateId": "tpl_1",
    "structureVersion": 3,
    "styleTemplateId": "style_2",
    "styleVersion": 1
  }
}
```

流式写作时可以逐章输出，但最终仍需发送一个完整、可保存的结构化结果。

### 8.1 项目已有接口基础

项目内的 Workflow API 资料和当前代码已经覆盖：

```text
POST /api/v1/kinsight-server/external/workflows/{app_id}/runs
```

并发送：

```json
{
  "inputs": {
    "query": "用户文本",
    "document": "文件文本"
  },

}
```

### 8.2 推荐输入 Schema

#### 结构提取 Workflow

```json
{
  "operation": "extract_structure",

  "max_heading_level": 2,
```

BFF 在调用前应通过 `/input-schema` 校验已发布 Workflow 的字段是否与前端版本匹配。

### 8.3 非流式与流式选择

| 任务 | 推荐模式 | 原因 |
| --- | --- | --- |
| 结构提取 | 非流式 JSON | 结果较短，必须完整通过 Schema 校验后才能编辑 |
| 风格提取 | 非流式 JSON | 结果较短，避免半截 JSON |
| 模板写作 | 流式 | 用户需要看到生成进度和逐步内容 |

如果非流式运行超时：

1. 从响应或响应头取得 `execution_id`。
2. 页面转为“后台提取中”。
3. 通过运行查询接口轮询。
4. 成功后取得输出，失败时展示具体错误。

### 8.4 SSE 事件映射

当前客户端已能处理以下事件：

| SSE 事件 | 页面行为 |
| --- | --- |
| `workflow:start` | 保存 `execution_id`，显示运行中 |
| `node:start` | 展示当前节点为执行中 |
| `node:end` | 标记节点成功或失败 |
| `RunContent` | 追加流式正文和思考摘要 |
| `workflow:end` | 完成运行并读取最终输出 |
| `error` | 展示错误信息 |

模板写作 Workflow 建议使用可读节点名称，例如：

- 解析模板。
- 检索参考资料。
- 生成章节。
- 统一风格。
- 校验文稿。

页面只展示节点名称和状态，不应展示模型内部推理过程。

### 8.5 BFF 改造建议

当前 `/api/chat/workflow` 只能接受：

```ts
{ message?: string; app_id: string; document?: string }
```

建议改为通用输入：

```ts
{
  app_id: string
  inputs: Record<string, unknown>
  stream?: boolean
  stream_output?: boolean
  include_events?: boolean
}
```

安全要求：

- 前端不能任意提交未经授权的 `app_id`，BFF 使用允许列表。
- `X-User-ID` 不能继续硬编码为 `kscc-user`，应来自真实登录态。
- API Key 只保存在服务端环境变量中。
- BFF 校验模板、文件和 Workflow 的访问权限。
- 对输入大小、超时和并发进行限制。

## 9. 页面与 AI 的状态衔接

### 9.1 模板提取状态

```text
idle
  ↓ 选择文件
file_selected
  ↓ 开始提取
uploading → parsing → extracting → validating
  ↓
reviewing
  ↓ 用户保存
saved
```

失败状态必须记录失败阶段：

- `upload_failed`
- `parse_failed`
- `workflow_failed`
- `schema_invalid`
- `permission_denied`
- `timeout`

用户可在失败后重试，不需要重新选择仍有效的文件。

### 9.2 提取结果确认

AI 结果必须进入编辑态，不允许自动保存。页面应额外展示：

- AI 提取标识。
- 整体置信度。
- 警告数量。
- 低置信字段提示。
- “查看原文依据”入口，按 `evidenceBlockIds` 定位来源。

用户保存后，AI 候选才转为正式用户模板。

### 9.3 模板写作入口

模板库卡片和详情页建议增加“立即使用”：

- 从结构模板进入：预选当前结构模板，再选择可选风格模板。
- 从风格模板进入：预选当前风格模板，再选择可选结构模板。
- 用户补充主题、事项、参考材料和占位符后开始生成。
- 请求中必须携带模板 ID 和版本，而不是只传模板名称。

## 10. JSON 可靠性与结果修复

结构和风格提取必须使用严格 JSON Schema：

1. 模型采用结构化输出能力时直接绑定 Schema。
2. 服务端解析 JSON。
3. 使用 Schema 校验类型、枚举、必填字段和层级关系。
4. 校验失败时把错误摘要交给“JSON 修复节点”重试一次。
5. 第二次仍失败则结束任务，不把残缺结果交给页面。

后处理不能依赖模型：

- 生成 UUID。
- 写入时间。
- 去除标题编号。
- 重新计算 `order`。
- 校验父子关系。
- 清理空要求和重复要求。
- 规范占位符。

## 11. 模型选择和参数建议

| 任务 | 模型要求 | 温度建议 | 输出长度 |
| --- | --- | --- | --- |
| 结构提取 | 中文长文理解、稳定 JSON | 0.1—0.3 | 2K—6K tokens |
| 风格提取 | 文体分析、稳定分类 | 0.1—0.3 | 1K—3K tokens |
| 章节写作 | 中文公文生成、事实约束 | 0.2—0.5 | 按章节篇幅动态设置 |
| 结果校验 | 规则判断、结构化输出 | 0—0.2 | 1K—3K tokens |

参数不应在前端写死。Workflow API 已支持运行时 `model_id`、`temperature`、`max_tokens` 等配置，应由工作流版本或服务端策略控制。

## 12. 安全与防编造规则

1. 不把上传材料用于当前任务以外的训练或复用，除非部署政策明确允许。
2. 模型上下文只包含当前用户有权访问的模板和文件。
3. 对文件解析结果执行敏感信息和提示注入防护。
4. 参考材料中的“忽略系统指令”等文本只能被视为资料内容，不能覆盖系统规则。
5. AI 不生成不存在的政策依据、文件编号、日期、金额、单位和责任人。
6. 缺失关键事实时询问用户或使用明确待补标记。
7. 模板提取只抽象结构或风格，不无必要地保留原文敏感事实。
8. 保存模板时记录 AI 工作流版本和人工确认状态，便于审计。

## 13. 质量评测

### 13.1 结构提取指标

- 标题识别准确率。
- 标题层级准确率。
- 父子关系正确率。
- 章节顺序一致率。
- 写作模式判断准确率。
- 生成提示词可执行性评分。
- 事实污染率，即模板中错误保留个案事实的比例。

### 13.2 风格提取指标

- 文种分类准确率。
- 行文方向准确率。
- 风格字段人工认可率。
- 写作要求重复率。
- 写作要求事实污染率。
- 多次运行一致性。

### 13.3 模板写作指标

- 必写章节覆盖率。
- 章节顺序和层级通过率。
- 篇幅命中率。
- 占位符完整填充率。
- 固定文本保持率。
- 关键事实可追溯率。
- 风格要求覆盖率。
- 人工首稿采纳率和平均修改次数。

- [ ] 文种明确时正确识别。

- [ ] 缺失占位符不会被模型编造。
- [ ] 参考文件只在有权限时可使用。

- `hooks/use-workflow-chat.ts`：Workflow SSE 事件解析。

- `workflow+api.docx`：Workflow 发布、输入 Schema、正式运行、查询、继续、取消和 SSE 事件等接口资料。
